**## 1. Project status and safe integration**

Back up the original frontend, backend and database. Copy the real source files into matching folders and merge carefully. **## 2. Final architecture**



\`\`\`text

Windows Setup.exe

  -> Electron main process

     -> starts local Node.js/Express backend

     -> waits for /api/health

     -> opens frontend in desktop window

        -> HTML/CSS/JavaScript

           -> local HTTP API

              -> routes -> middleware -> controllers

                 -> services -> repositories

                    -> local MySQL Server

                       -> persistent database directory

\`\`\`



Frontend code must never connect directly to MySQL or contain database credentials. Local features can work offline; cloud APIs, remote authentication, external fonts/media and cloud backups still need internet unless replaced with offline alternatives.

**## 8. EXE method A — Electron Builder + NSIS**

This is the recommended direct path for generating the Windows Setup `.exe` using the current root `package.json` scripts. Run all commands from the project root in PowerShell.

### 8.1 Check Node.js and install dependencies

```powershell
where.exe node
node --version
npm install
npm --prefix backend install
npm run check:structure
```

### 8.2 Prepare the bundled Node.js runtime

The current `backend-manager.js` standalone-runtime approach expects this file before packaging:

`installer/runtime/node/node.exe`

If Node.js is installed on the build computer, copy its executable with PowerShell:

```powershell
New-Item -ItemType Directory -Force ".\installer
untime
ode"
$nodePath = (Get-Command node.exe).Source
Copy-Item $nodePath ".\installer
untime
ode
ode.exe" -Force
Test-Path ".\installer
untime
ode
ode.exe"
& ".\installer
untime
ode
ode.exe" --version
```

The `Test-Path` command must return `True`. If Node.js is not installed, obtain a compatible Windows runtime from https://nodejs.org/en/download and place `node.exe` at that exact path. Validate the chosen Node.js version and architecture with the backend on a clean Windows machine; copying the build computer's runtime alone does not guarantee production compatibility.

### 8.3 Build and inspect the unpacked app

```powershell
npm run build:dir
```

Inspect the generated directory under `release`. Verify that it contains `resources
untime
ode
ode.exe` and the backend source/dependencies at the exact paths used by `desktop/lifecycle/backend-manager.js`. If these files are missing, check `build.extraResources` in `package.json` before continuing.

### 8.4 Generate the installer EXE

```powershell
npm run build:win
```

The installer should appear in `release`, with a name similar to `Skill-Tech-Setup-1.0.0-x64.exe`. The actual filename depends on the package version and target architecture.

### 8.5 Install and test

Install the newly generated EXE, then test on a clean Windows VM without XAMPP, Node.js or developer tools. Verify original pages, API startup, database provisioning, login/CRUD, offline operation, restart persistence, backup/restore, upgrade and uninstall.

**Warning:** A successful build only proves that packaging completed. It does not prove that the backend runtime paths, dependencies, or MySQL provisioning work on a customer's computer. MySQL Server is not installed by `mysql2` or by bundling `node.exe`.

**## 10. MySQL offline installation requirements**



\`mysql2\` is a Node.js client; it does not install MySQL Server. Production setup must select a supported/licensed distribution and implement:

1\. OS/permissions/disk preflight.

2\. MySQL install or documented existing-server setup.

3\. Dedicated database and least-privilege account.

4\. Protected credentials outside install folder.

5\. Persistent data outside install directory.

6\. Service startup/readiness and port-conflict handling.

7\. Versioned migrations with history.

8\. Backup, restore, upgrade and rollback.

9\. Uninstall that preserves customer data by default.



Never silently overwrite an existing database/server. Never embed production passwords or JWT secrets in frontend files or a packaged \`.env\`.



**## 11. Security checklist**



\- Electron \`contextIsolation: true\`, \`nodeIntegration: false\`, sandbox where compatible.

\- Narrow preload API; no arbitrary filesystem/shell/IPC bridge.

\- Backend validation and parameterized SQL.

\- Local API bound to loopback where appropriate, with protection against unauthorized local requests.

\- Restrict navigation, external links, permissions and Content Security Policy.

\- Keep production secrets out of packaged resources.

\- Store logs in app-data and redact tokens/passwords/private records.

\- Handle port conflicts; port 4317 is only a development example.

\- Code-sign the installer where practical.

**## 13. Troubleshooting**



\- **\*\*Blank window:\*\*** inspect Electron logs, page/asset paths, Content Security Policy and API readiness.

\- **\*\*Backend does not start:\*\*** check packaged server path, runtime compatibility, child-process logs and port conflicts.
\- **\*\*`node.exe` missing after install:\*\*** verify `installer/runtime/node/node.exe` exists before building, confirm `extraResources` copies it to `resources/runtime/node/node.exe`, run `npm run build:dir`, inspect the unpacked output, then run `npm run build:win`.
\- **\*\*`node.exe` missing after install:\*\*** verify `installer/runtime/node/node.exe` exists before building, ensure `extraResources` copies `installer/runtime/node` to `runtime/node`, run `npm run build:dir`, inspect the unpacked `resources/runtime/node/node.exe`, then rebuild the installer. PowerShell checks: `Test-Path ".\installer\runtime\node\node.exe"` and `& ".\installer\runtime\node\node.exe" --version`.

\- **\*\*Database disconnected:\*\*** check service, host, port, database, credentials, privileges and migrations. Do not delete customer data as a quick fix.

\- **\*\*Inno Setup source missing:\*\*** verify \`.iss\` source path and actual unpacked app directory.

\- **\*\*Works only on developer PC:\*\*** test on clean Windows VM; build machines may have undeclared runtimes/settings.

\- **\*\*Data missing after upgrade:\*\*** stop the app, preserve files/logs, review migration history and restore a verified backup. Never overwrite populated data without a controlled migration/backup plan.

The project is complete only after the original source is integrated, MySQL provisioning and migrations are implemented, packaged backend startup is verified, and a clean Windows test proves the branded installer works without XAMPP/developer tools while preserving customer data.
